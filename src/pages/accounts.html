Account lifecycle

Accounts can be deleted, restored, and downloaded. Deletion happens over a period of time rather than all at once.

Deletion is a window

  1. A member asks to be deleted. The account moves to PENDING_DELETION, deletion_scheduled_at is set, and they're emailed the date.
  2. Reminders go out five days and one day before the date. Each one is recorded in user_deletion_reminders, so a retried run can't send the same warning twice.
  3. A signed restore link in every email (/account/restore/{user}) cancels the deletion without signing in.
  4. When the window ends, the nightly account:process-deletions run anonymizes the account if it has history worth keeping, or removes it outright if not.

user.account-deletion-days sets the window, clamped to 1–365 in code. user.anonymous-after-deletion chooses between anonymizing and removing.

Unverified accounts

An account that never verifies its address holds a unique email forever. account:prune-unverified (daily, 08:30) deals with them:

  • Warned first, then removed. One warning goes out once the notice days have passed since sign-up (default 2). The account is removed once the grace period after that warning has passed (default: delete on day 3). The grace period counts from the warning, so nobody is removed on the same run that warns them.
  • Never while verification is off, because then every account is unverified.
  • Only active member accounts. Admins, newsletter rows, accounts already pending deletion, and any account with ledger rows are never touched.
  • Removal goes through AccountDeletionService::hardDelete(), and each one is also written to the ezeh log channel, because a scheduled run has no signed-in actor to audit.

The settings are on Site configuration → Security, under Email Verification: email-settings.unverified-auto-delete, unverified-notice-days and unverified-delete-days.

"We missed you"

account:send-inactivity-reminders (daily, 10:00) emails a member who hasn't been seen for 30 days. Only one is sent per absence: another goes out only after the member has been back. While verification is on, only verified addresses are emailed. Suspended accounts, admins and accounts never seen at all are skipped. The settings are user.inactivity-reminder and user.inactivity-reminder-days.

Both emails are template-builder slots (SystemEmailEnum::UNVERIFIED_WARNING and INACTIVITY_REMINDER). Both commands take --dry-run. Run the prune with it once before its first real night on an install that already has unverified sign-ups.

Deleted accounts

Anonymized rows are soft-deleted, so every ordinary query skips them, including the users listing, its metrics and its search. They appear only under Admin → Deleted accounts, where they can be restored or purged for good.

To reach one in code, use AccountDeletionService::trashedQuery(). A plain User::find() returns null for all of them.

Download a copy

At /app/account/download-data, behind user.allow-data-download, AccountDataExportService produces one JSON document containing the profile, the ledger, the consent history and both library indexes.

The password hash and its history, the two-factor secret, the recovery codes and the admin gate map are deliberately left out. They're data about the account rather than data belonging to the person, and including them would only make a leaked export more damaging.
