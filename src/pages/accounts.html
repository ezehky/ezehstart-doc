Account lifecycle

Accounts can be deleted, restored, and downloaded. Deletion happens over a period of time rather than all at once.

Deletion is a window

  1. A member asks to be deleted. The account moves to PENDING_DELETION, deletion_scheduled_at is set, and they're emailed the date.
  2. Reminders go out five days and one day before the date. Each one is recorded in user_deletion_reminders, so a retried run can't send the same warning twice.
  3. A signed restore link in every email (/account/restore/{user}) cancels the deletion without signing in.
  4. When the window ends, the nightly account:process-deletions run anonymizes the account if it has history worth keeping, or removes it outright if not.

user.account-deletion-days sets the window, clamped to 1–365 in code. user.anonymous-after-deletion chooses between anonymizing and removing.

Deleted accounts

Anonymized rows are soft-deleted, so every ordinary query skips them, including the users listing, its metrics and its search. They appear only under Admin → Deleted accounts, where they can be restored or purged for good.

To reach one in code, use AccountDeletionService::trashedQuery(). A plain User::find() returns null for all of them.

Download a copy

At /app/account/download-data, behind user.allow-data-download, AccountDataExportService produces one JSON document containing the profile, the ledger, the consent history and both library indexes.

The password hash and its history, the two-factor secret, the recovery codes and the admin gate map are deliberately left out. They're data about the account rather than data belonging to the person, and including them would only make a leaked export more damaging.
