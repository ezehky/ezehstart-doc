Image and video libraries

Two libraries with the same design, so a screen that knows one already knows the other.

What both share

  • Folders: a folder tree per library.
  • Visibility per item (MediaVisibilityEnum): private, role, or public. It decides what a signed-out visitor can see. It doesn't open anything to members.
  • A delete guard backed by a usage table (image_usages, video_usages) with a restricting foreign key. An item in use on a published post refuses to be deleted, so the post never ends up with a broken picture.
  • Pickers: <x-form.image-slot> and <x-form.video-slot>.
  • Available in both workspaces. A member's library holds only what that member uploaded, in the grid and in every picker, however the site's own media is marked. isVisibleTo() applies the same rule, so an id sent by hand gets no further. A member's uploads don't appear in the admin library either. Admins reach them only from the account page.
  • When someone at the site changes something in a member's library, UploadModifiedEmail tells the member.

Images

  • Upload several images at once, and search by name.
  • Rename without changing the URL: the title changes, but the stored path doesn't.
  • Members have a configurable quota. Administrators don't.
  • Crop in place. Select one JPEG, PNG or WebP image and open Crop. The file is cut and written back over itself, so its URL doesn't change and every post already using it shows the cropped version. GIF (animation) and SVG (no pixels) are refused. ImageLibraryService::canCrop() and crop() do the work, and the library's tiles use Image::previewUrl(), which adds ?v={updated_at} so the crop shows straight away. Posts keep the plain url().
  • WebP on the way in. With Convert photos to WebP on (Configuration › Security, uploads.convert-to-webp, on by default), JPEG and PNG uploads are re-encoded at quality 80 and scaled to 2560px on the longest side. GIF and SVG are kept as they are. A conversion that comes out larger, or fails, keeps the original, so an upload never fails here. It needs GD built with WebP.
  • Uploads are optimised with spatie/laravel-image-optimizer when jpegoptim, optipng and pngquant are installed. Without them, uploads still work, just unoptimised.
  • A folder you've just made opens straight away, in both libraries, since the next upload is usually headed there.

Desktop Outlook can't show WebP. If library images go out in email, turn the conversion off. Files already stored aren't touched either way.

Folder import

Administrators get an Import tab that takes whole folders, picked or dropped, and rebuilds them as library folders, up to eight levels deep.

  • The settings are chosen once, before anything is sent: the parent folder, visibility, shared or personal, and whether to keep the folder structure. They're locked for the rest of the import.
  • The browser sends the images ten at a time (resources/js/folder-import.js), well under PHP's file-upload limit and the request time limit.
  • A folder already there with the same name in the same place is reused, so importing the same folder twice fills one tree. ImageLibraryService::folderForPath() does the matching.
  • When a single folder was imported, the library opens it at the end.
  • Members never see the tab, and every method checks again on the server.

File storage

Uploads can be kept on Cloudflare R2 instead of the local public disk. It's optional and off by default. Configuration › File storage (admin.config.file-storage, gate config.file-storage) has the switch (storage.cloud) and the bucket's public address (storage.public-url). The access keys, bucket and endpoint stay in .env as R2_*, so a secret is never written to the site configuration or shown on a screen. CloudStorageService does the work over the r2 disk.

  • Every upload lands locally first, where it's converted to WebP, optimised and measured, and is then promoted to R2. A crop pulls an R2 file down, cuts it and pushes it back.
  • Each image records its disk in images.disk, and is cropped and deleted through it. The logo and favicon have no row, so they're looked for on the active disk first, then the other one.
  • Flipping the switch moves nothing. It decides where a new upload goes, and every existing file keeps working where it is. Sync on the same screen moves the rest onto the disk that's switched on, ten files per request, with the logo and favicon in the first batch. A file that can't be moved is skipped and reported, so the sync always finishes. It's logged once, as STORAGE_SYNC.
  • A switch without its keys counts as off. R2 is used only once every R2_* key is set and there's a public address, since a file in a bucket the browser has no address for is a file nobody can see. Until then uploads stay local, Sync refuses to run, and the screen names the missing keys.
  • Videos are references, not files, so there's nothing of theirs to store.

Videos

A video row is a reference (a provider plus that provider's own id), never a file and never a URL. The player URL is rebuilt from that pair every time it's rendered, so there's no author-supplied URL stored in the row to be trusted later.

  • VideoProviderEnum is an allowlist: YouTube and Vimeo.
  • uploads.user-video-limit (default 25) caps a member's library. It isn't about storage, since a video uses no disk space. It keeps the library usable.
  • Videos embedded in a post body are claimed from the saved HTML by VideoLibraryService::syncFromHtml().
