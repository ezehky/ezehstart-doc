Image and video libraries

Two libraries with the same design, so a screen that knows one already knows the other.

What both share

  • Folders: a folder tree per library.
  • Visibility per item (MediaVisibilityEnum): private, role, or public.
  • A delete guard backed by a usage table (image_usages, video_usages) with a restricting foreign key. An item in use on a published post refuses to be deleted, so the post never ends up with a broken picture.
  • Pickers: <x-form.image-slot> and <x-form.video-slot>.
  • Available in both workspaces. A member's uploads are private to them and don't appear in the admin library. Admins reach them only from the account page.
  • When someone at the site changes something in a member's library, UploadModifiedEmail tells the member.

Images

  • Upload several images at once, and search by name.
  • Rename without changing the URL: the title changes, but the stored path doesn't.
  • Members have a configurable quota. Administrators don't.
  • Uploads are optimised with spatie/laravel-image-optimizer when jpegoptim, optipng and pngquant are installed. Without them, uploads still work, just unoptimised.

Videos

A video row is a reference (a provider plus that provider's own id), never a file and never a URL. The player URL is rebuilt from that pair every time it's rendered, so there's no author-supplied URL stored in the row to be trusted later.

  • VideoProviderEnum is an allowlist: YouTube and Vimeo.
  • uploads.user-video-limit (default 25) caps a member's library. It isn't about storage, since a video uses no disk space. It keeps the library usable.
  • Videos embedded in a post body are claimed from the saved HTML by VideoLibraryService::syncFromHtml().
