Going to production

A checklist for turning the kit into a live product.

Identity and branding

  • Rename your product. Set APP_NAME and the site name under Site configuration → Info. Your product mustn't be called "Ezeh Start". See the trademark policy.
  • Replace the logo, favicon and support contacts.
  • Pick your colour under Configuration › Brand colour. The site, Flux's accent and the email builder follow it without a rebuild.
  • Change or remove the seeded admin admin@example.test / password.

Legal

  • Replace the demo policies with terms, privacy and cookie policies written for your business. Publish them as a new version.
  • Setting a Google Analytics ID turns the cookie banner into a consent choice on its own. If you add any other optional cookie (advertising, a chat widget), add a CookieCategoryEnum case for it, load it only when CookieConsentService::granted() says so, and raise the consent version. See The cookie banner.
  • Name Google Analytics in your cookie and privacy policies once an ID is set.
  • Decide on account-deletion and activity-log retention windows, and document them in your privacy policy.
  • Keep the MIT copyright notice that ships with the kit (see License).

Infrastructure

  • APP_ENV=production, APP_DEBUG=false, and a production database.
  • A mail provider picked on Email settings › Delivery, with a test email sent. Until one is picked, email goes to the log.
  • Open /robots.txt and /sitemap.xml on the live domain, and submit the sitemap to Google Search Console. Make sure no public/robots.txt is shadowing the app's.
  • If uploads should live on Cloudflare R2, set the R2_* keys, switch it on under File storage, and run Sync to move the files already uploaded.
  • A cron entry for the scheduler and a supervised queue worker.
  • Back up the site configuration file on the local disk as well as the database. It isn't a table.
  • Install jpegoptim, optipng and pngquant if you want uploads optimised.
  • Set the Turnstile keys before turning the captcha on.
  • For payments: set live keys for each vendor you use, run php artisan payments:health, and register /webhooks/payments/{vendor} in each vendor's dashboard. Keep PAYMENTS_WEBHOOK_VERIFY_SIGNATURE on. See Payments and subscriptions.
  • Replace the example SubscriptionFeatureEnum cases and the three placeholder contact locations.

Security review

  • Review every custom role's gate map. New screens start open for broad roles.
  • Decide whether two-factor, passkeys and social sign-in should be on.
  • Check who holds the impersonation ability.
