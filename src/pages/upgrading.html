Releases and upgrading

How versions are numbered, and what taking a new one involves.

Versioning

The kit follows Semantic Versioning and records every change in CHANGELOG.md, using the Keep a Changelog format.

  • A minor release may add tables, enum cases and route names. It won't rename existing ones.
  • A major release is the only kind that renames things.

If you're starting a project from the current kit, there's nothing to do. The sections below are for a project built on an earlier version.

Upgrading to 2.3.0

There are no migrations. Rebuild the front end:

npm run build

Convert the stored policy and FAQ text to HTML, once. An existing install holds it as markdown, and the public pages now print it as HTML. Run this in php artisan tinker or a one-off migration. It doesn't touch updated_at, so the date on a legal page stays the same: 

use App\Services\BlogService;
use App\Services\MarkdownService;
use Illuminate\Support\Facades\DB;

$toHtml = fn (?string $markdown) => app(BlogService::class)->sanitize(app(MarkdownService::class)->toHtml($markdown));

DB::table('faqs')->orderBy('id')->each(fn ($row) => DB::table('faqs')->where('id', $row->id)->update(['answer' => $toHtml($row->answer)]));
DB::table('policies')->orderBy('id')->each(fn ($row) => DB::table('policies')->where('id', $row->id)->update(['content' => $toHtml($row->content)]));

Run it once only. MarkdownService escapes raw HTML, so a second run turns the converted text back into visible tags.

  • Changes you made to the old pages::site.home or pages::site.blog.* Livewire pages move to resources/views/site/ and the matching Site\ controller.
  • <x-form.markdown-field>, kMarkdownFormat() and .markdown-prose are gone. Use <x-form.rich-text>, save through BlogService::sanitize(), and style with .rich-prose.
  • Existing lime-* classes still render correctly. Write new ones as brand-*.
  • Processing fees start at zero, so nothing customers pay changes until you set one. See Payments.

Upgrading to 2.2.1

Nothing to migrate. If the config is cached, rebuild it so the new payments log channel is registered:

php artisan config:cache

Upgrading to 2.2.0

php artisan migrate

That creates the payment and subscription tables. transaction_gateways needs five columns by hand, because they were folded into its create migration, which an existing install has already run. Add them in a migration of your own: 

Schema::table('transaction_gateways', function (Blueprint $table) {
    $table->string('currency', 10)->nullable()->after('vendor');
    $table->string('channel', 100)->nullable();
    $table->string('failure_reason')->nullable();
    $table->timestamp('paid_at')->nullable();
    $table->timestamp('verified_at')->nullable();
});

The kit's other add_* migrations were folded into their create_*_table files too, but those columns already exist on a 2.1.0 install. Don't run migrate:fresh to catch up.

  • Copy the payments block from .env.example, fill in the vendors you'll use, and run php artisan payments:health.
  • Register https://your-site/webhooks/payments/{vendor} in each vendor's dashboard.
  • Run a queue worker and the scheduler. Three scheduled commands are new.
  • Replace the example SubscriptionFeatureEnum cases before creating plans.
  • Grant the payments and subscriptions gates to the roles that need them.

See Payments and subscriptions.

Upgrading to 2.1.0

php artisan migrate
php artisan lang:translate fr
php artisan lang:translate es

The migration adds two nullable columns to users. Two scheduled commands are new and both are on by default. Run php artisan account:prune-unverified --dry-run once before the first real night on an install that has been collecting unverified sign-ups, to see who it would warn. See Account lifecycle.

A test that expected forgot password to refuse an unknown address now gets the code step instead.
