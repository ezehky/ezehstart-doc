Search engines and analytics

What the site tells crawlers about itself, how Google Analytics is switched on, and the cookie banner that decides whether it loads.

robots.txt and the sitemap

/robots.txt (robots) and /sitemap.xml (sitemap) are written by the app, in SearchEngineService, not kept in public/. A crawler wants the sitemap's full address, and a static file can't know which domain it's served from, so the same build works on staging and live.

  • robots.txt allows everything and points at the sitemap. It never names a workspace: a Disallow line is a public list of the paths a site would rather nobody looked at.
  • The workspaces say noindex instead. NoIndexMiddleware on both workspace groups sends X-Robots-Tag: noindex, nofollow, and they sit behind a sign-in anyway.
  • The sitemap lists the home page, the blog index, every live post (with its lastmod) and the legal pages. Nothing drafted, scheduled or private appears. The list is cached for an hour under sitemap.urls.

A public/robots.txt wins. The web server serves a static file before the request reaches Laravel, so delete any you added.

Blog feed

/blog/feed (blog.feed) is RSS 2.0 of the latest twenty live posts: title, excerpt, author, categories and image, each linking to the post page. The body is never in the feed. The public layouts advertise it with a <link rel="alternate">, so feed readers find it from any page.

Google Analytics

Paste a GA4 measurement ID (G-…) under Configuration › Site info. It's stored as analytics.ga4-id in the site configuration, not .env, because it's a public identifier printed in every page that loads the tag, not a secret. AnalyticsService and <x-site.analytics> do the rest.

  • Public pages only. Neither workspace loads the tag, and neither does a session an administrator is impersonating: their clicks aren't a visitor's.
  • Page views only. Nothing about the visitor or their account is sent.
  • Only after consent. Until the visitor allows measurement, the tag waits in the browser and doesn't load.
  • An ID that isn't the G- shape is ignored, as if none were set.

The cookie banner

preferences.accept-cookies (on by default) shows the banner, a card in the bottom corner. It takes one of two shapes, decided by whether there's anything optional to allow:

Analytics IDShapeAnswers
Not setA notice. The site sets only session and CSRF cookies, which a notice coversGot it
SetA choice. Nothing optional loads until it's madeAccept all, Reject optional, or Manage preferences for a switch per category
  • Categories are CookieCategoryEnum cases: necessary (always on) and measurement. Add a case when you add another kind of optional cookie.
  • The answer is one plain cookie, site_consent, holding something like v1:necessary,measurement for 180 days. It's left out of cookie encryption in bootstrap/app.php because the browser writes it. CookieConsentService::granted() reads it on the server.
  • The site never assumes a yes. No answer, an old version, or the banner switched off all read as necessary only. Turning the banner off means analytics never loads.
  • Cookie settings appears in the footer once there's a choice to make, and reopens the banner with the switches showing.
  • Taking a category back reloads the page. A script that has already run can't be unrun, so the reload starts again without it, and the analytics tag clears its cookies.
  • Changing the categories? Raise CookieConsentService::VERSION, and every visitor is asked again.

The banner's wording is generic. Say what you actually measure in your cookie policy, and name Google Analytics there once you've set an ID. See Legal pages and consent.
