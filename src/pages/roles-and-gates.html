Roles and gates

Roles decide how far into the admin workspace someone can go. Gates enforce it in two places.

Roles

A role is a database row, not an enum case, so administrators create and edit roles from Admin → Roles. An admin can hold any number of roles through the role_user pivot.

Each role holds a gate map: a level of access for each area of the admin workspace. When an admin has several roles, the maps are merged and the highest access wins each key. A second role can therefore only widen what someone reaches. A personal override on the account sits on top of the merged result, and it's the only thing that can narrow it.

The Manage roles modal enforces two rules: you can't revoke your own admin role, and you can't revoke the last one.

Access levels

GateAccessEnum, from least to most:

noneCan't open the screen
viewCan read
modifyCan edit existing rows
createCan add rows
fullEverything, including delete

The levels form a ladder: full includes create, which includes modify, which includes view. A screen only asks for the lowest level it needs.

Inheritance

Gate keys are dotted, for example users.deleted-accounts. A child key with no gate of its own inherits its parent's. That means a new screen starts closed for narrow roles and open for broad ones: users.deleted-accounts opens for a role holding users, but stays shut for a role holding only users.users-list. The protected admin role needs nothing granted. A custom role does.

Gated twice

Every action button is gated in two places:

  1. <x-dashboard.gate.button> or <x-dashboard.gate.menu-item> hides it, and
  2. the Livewire method behind it checks again with kGate().

Hiding a control is a courtesy. The method check is what actually protects the action. Whole screens are closed the same way: setPageGate() from WithGateProps names the gate a screen sits behind, so typing the URL doesn't get around a hidden sidebar entry.

The Author role

A seeded Author role limits an account to the posts it wrote and gives it a public byline, with the bio and social handles on user_profiles. The blog looks the role up by its slug, so you can rename it or change its gates freely.
